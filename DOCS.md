# Calypso Gallery - Architecture, Cryptography & User Guide

Calypso Gallery is a privacy-first, security-hardened open-source media gallery for Android. In addition to standard gallery capabilities, it features **hardware-level memory zeroization**, **Argon2id and AES-256 cryptographic vaults**, **zero-storage-footprint virtual albums**, and **advanced video player buffering and frame caching optimizations**.

---

## 1. Storage & On-Disk Architecture

All standard application-managed data generated by Calypso Gallery (`Virtual Album Saves/` and `Favorites/`) is organized centrally under `Internal Storage > Calypso Gallery`, a standalone top-level folder in internal storage (it is **not** nested inside `Documents`).

By default, the cryptographic vault container (`Secrets/`) also lives inside `Internal Storage > Calypso Gallery > Secrets` for zero-friction standard mobile usage. Optionally, you can configure a **Custom / External Storage Vault Location** (for example, an external USB flash drive, microSD card, or custom directory) so `Secrets/` resides directly on external media with **zero encrypted vault footprint on the phone's internal storage**—supporting both direct mobile playback and a planned RAM-only desktop viewer.

> [!NOTE]
> **Android USB / External Filesystem Requirement:** Direct zero-disk `AES-256-CTR` random-access streaming and decryption operate over `java.io.File` / `RandomAccessFile` on a POSIX-mounted, writable directory (internal storage, mounted microSD card, or kernel-mounted USB volume). `CryptoManager.resolvePickedPathToFile` (used by `validatePickedVaultDirectory`) accepts direct POSIX paths cleanly—including real `/storage/<UUID>/...` volumes that Fossify's `isPathOnOTG()` would otherwise reject whenever `MainActivity.checkOTGPath()` stores that mount path in `config.OTGPath`—and maps `otg:` pseudo-paths and `content://` tree/document URIs to POSIX mount roots (`/storage/...`, `/mnt/media_rw/...`, `/mnt/runtime/...`, `DocumentsContract`, `/proc/self/fd` `Os.readlink`) before verifying writeability with `CryptoManager.canWriteToDirectory`. If a device or ROM exposes a USB drive strictly through Android's virtual Storage Access Framework (`otg:/` or `content://`) with no accessible POSIX mount directory or writable `java.io.File` handle, it cannot be used as a direct vault root and is rejected with an explanatory prompt (`usb_direct_filesystem_required`).

### A. `Virtual Album Saves/` (Standard Virtual Albums)
- Contains JSON manifests for virtual albums created from unencrypted, standard physical folders.
- The filename matches the display name of the virtual album (e.g., `Vacation.json`).
- Stores references to original file paths on disk without duplicating data. Adding a photo to any number of virtual albums uses zero additional storage space.
- Every entry carries both the **file identity** (`mediaStoreId`, `fileSize`, `lastModified`, `fingerprint`) and a zero-pollution **folder identity** (`folderInode`, `folderSignature`, `capturedAtSec`), enabling reliable recovery after renames or folder moves while preventing false matches in unrelated directories.

### A2. `Favorites/` (Favorites Backup)
- Contains `favorites.json`, the backup of the favorites.
- It lives on the shared storage, outside of the app sandbox, so it survives a wipe of the app data and is restored when the app starts without any data.
- The backup is only written while the app may access the shared storage.
- The entries carry the same file and folder identity metadata as the virtual album manifests (`mediaStoreId`, `fileSize`, `lastModified`, `fingerprint`, `folderInode`, `folderSignature`, `capturedAtSec`), so a favorite survives external renames and moves without touching user folders.

### B. `Secrets/` (Cryptographic Vault Container)
Created when the user enables password protection for hidden items in Settings or chooses a custom/external vault location:

> **Folder rename / backward compatibility.** The container was previously named `Cipher_Secrets/`. New vaults use `Secrets/`, but the on-disk format is identical and existing folders are never renamed by an upgrade: the stored absolute `vaultRootPath` is honoured, and both folder names are accepted by vault detection (`resolveExistingVaultInDirectory`, `internalVaultCandidates`), custom-location creation, external sync source resolution (`resolveSyncSourceRoot`), export targeting, deletion, and stealth `JSON/` manifest path remapping. External drives with an existing `Cipher_Secrets/` container keep using it. `LEGACY_CIPHER_APP_DIR_NAME` and `LEGACY_VAULT_DIR_NAME` (CLI) are historical on-disk values required for migration, not product names.
- **`.nomedia` Placement Rules:** `.nomedia` belongs at the **vault container root** (`Secrets/.nomedia`), instructing Android's `MediaScanner` to ignore the entire directory tree without marking individual physical albums as excluded. Normal physical albums and the Default Secret Album (`__VAULT_DEFAULT_ALBUM__`) do **not** receive an inner `.nomedia`. In accordance with `ExcludedMenuPolicy.isEncryptedAlbumExcluded`, only explicitly `.`-prefixed hidden albums inside the vault receive an inner `.nomedia` (created by `CryptoManager.createHiddenPhysicalAlbum` or the Desktop CLI's `write_encrypted_folder_meta`), keeping normal vault albums directly visible once unlocked (while the Encrypted Vault Recycle Bin is always exempted from exclusion by `isVaultRecycleBin`).
- **`.vault` (Master Vault Header):** Stores the encrypted 256-bit Master Encryption Key (MEK), protected via `Argon2id` (64 MB RAM cost, 3 iterations, 2 threads) and `AES-256-GCM`.
- **`JSON/` (Stealth Encrypted Virtual Albums):**
  - When a virtual album is created from contents of a hidden/encrypted physical album, it automatically gains **Stealth Virtual Album** status.
  - The filename is an obfuscated 16-character hexadecimal identifier (`fva_8f4b1e2a9c3d4e5f.json`), derived via HMAC-SHA256 with MEK.
  - The album title, member file paths (`fullPath` + vault-relative `relativeVaultPath`), and parent folder reference (`relativeParentVaultPath`) within the JSON payload are encrypted via `AES-256-GCM` with the `FVSTR1:` prefix. Inspecting the file on disk reveals neither the album name nor any media paths, while relative paths allow external USB/SD vaults to resolve seamlessly across different mount points/UUIDs (see [Section 5](#5-device-migration-backup--vault-auto-detection)). `tools/fossify-cipher-cli/cipher_vault.py` never reads, writes, or modifies `JSON/`.
- **Randomized Vault Subfolders (`a1b2c3/`):**
  - Encrypted physical albums are moved inside `Secrets` under randomized 6-character hex subfolder names.
  - Original album names are encrypted and saved in `.meta` (`FGMETA2`) via `AES-256-GCM`.
  - All media files are converted to randomized `.bin` files (`<random_hex>.bin`), and original plaintext files are securely shredded.

## 2. Cryptographic Specifications & Bit-Rot Resilience

Calypso Gallery employs a defense-in-depth cryptographic pipeline designed to prevent data leakage, mitigate offline brute-force attacks, and isolate corruption:

| Component                   | Primitive / Algorithm                                           | Purpose                                                                   |
| :-------------------------- | :-------------------------------------------------------------- | :------------------------------------------------------------------------ |
| **Key Derivation (KDF)**    | `Argon2id` (64 MB RAM, 3 iterations, 2 threads)                 | Hardware-hardened key derivation resistant to GPU/FPGA/ASIC cracking      |
| **Hardware Key Protection** | Android Keystore (`AES-256-GCM`, StrongBox / TEE)               | Device-bound cryptographic wrapping layer (`vaultWrappedKeyData`)         |
| **Vault Headers & Strings** | `AES-256-GCM` (`12-byte IV`, `128-bit Tag`)                     | Authenticated encryption for headers, thumbnails, and metadata            |
| **Payload Streams**         | `AES-256-CTR` (`16-byte IV` with counter derivation)            | Random-access streaming encryption for images and high-bitrate videos     |
| **Integrity Verification**  | `Poly1305-AES` MAC (`16-byte Tag`) with AAD Header Binding      | Cryptographic tamper detection during export, streaming, and decryption   |
| **Pre-Wipe Verification**   | SHA-256 Digest Verification + Decryption Readback               | Guarantees file is 100% decryptable before original plaintext is touched  |
| **Screen & Recents Guard**  | `FLAG_SECURE` + Android 13+ Recents Suppression                 | Prevents screen capture, video recording, and task switcher leakage       |
| **Data Destruction**        | Full-file CSPRNG overwrite (1 MiB chunks) + `fsync` + `syncDir` | Best-effort shredding subject to flash controller wear-leveling realities |

> **Release 1.20 (accepted ADR [`docs/adr/0001-tink-streaming-aead-migration.md`](docs/adr/0001-tink-streaming-aead-migration.md)) changes the payload scheme to Tink `AES256_GCM_HKDF` streaming AEAD (container version 4) and adds per-file DEKs + rotatable KEKs. Metadata moves to per-record AES-GCM with context-binding AAD. Both v3 and v4 containers remain readable and writable. The complete corruption / bit-rot behaviour — which differs between v3 and v4 — is specified in [§2.4](#24-corruption--bit-rot-behaviour-v3-today-v4-in-120); this section's CTR error-isolation description applies to v3.**

> **Operational security (accepted [ADR 0002](docs/adr/0002-operational-security-hardening.md)):** OS CSPRNG only (no user-movement entropy); **"Brute-Force direnci"** setting (default: target vault unlock time 2.0–7.0 s with decimal input; alternative: ready-made Argon2id modes) whose calibrated KDF parameters are stored in `.vault`, like KeePass stores rounds in `.kdbx` — see [the calibration methodology](docs/argon2-calibration-methodology.md); trace-hygiene audit (thumbnail cache, recents snapshot, MediaStore, temp files, backups, clipboard, keyboard); immediate key zeroization except while a registered foreground file operation is active; durable/resumable secure wipe. These apply to both v3 and v4 vaults.**

### Bit-Rot Resilience (Zero Error Propagation)
Monolithic container formats (such as Veracrypt volumes or ZIP archives) risk total catastrophic loss if a single sector corrupts. Calypso Gallery avoids this through granular file isolation:
1. **File-Level Granularity:** Each image and video is stored as an independent encrypted binary file. Corruption in one file has **zero effect** on any other file or the vault at large.
2. **CTR Mode Error Isolation:** `AES-256-CTR` operates as a stream cipher (`Ciphertext = Plaintext ⊕ Keystream`). A 1-bit corruption in ciphertext affects **only that exact single bit** upon decryption. Adjacent bytes and the rest of the file remain intact. In JPEG photos, bit-rot results only in a minor visual artifact rather than complete decode failure; in MP4 videos, only a single corrupted microsecond frame occurs while the rest of the stream continues playing.
3. **Hardware-Bound & Redundant Keying:** Vault credentials on disk (`.vault`) are backed by an Android Keystore hardware-bound wrapping layer (`vaultWrappedKeyData`) with StrongBox / TEE enforcement. If the master header file suffers physical sector loss, the application can recover the master key bundle on the authenticated device.

> **v4 note:** the streaming AEAD authenticates data in segments, so a corrupt segment is *detected* rather than silently displayed. The app substitutes placeholder bytes for that segment only and keeps playing (§2.4). Bit-rot isolation is therefore **per-segment**, not per-bit; the reader throws on a bad segment and does not skip it on its own — the tolerant substitution is explicit application logic.

### 2.1 `Poly1305-AES` Compatibility (restic)

The payload MAC uses the **Poly1305-AES128** construction (Bernstein, 2005) exactly as implemented by [restic](https://github.com/restic/restic) in `internal/repository/crypto`:

```
one-time key = clamp(r) || s
  r = macKey[0:16]                       (fixed per vault)
  s = AES-128_K(macKey[16:32], contentIv) (derived per file from the random 16-byte IV)
```

BouncyCastle's `Poly1305(AESEngine)` implements the identical construction (`key[0:16]` → `r`, `key[16:32]` → AES-128 key), so the Android app, the desktop CLI (`tools/fossify-cipher-cli`) and restic produce byte-identical containers. The four published test vectors from the original paper (`cr.yp.to/mac/poly1305-20050329.pdf`) are asserted on **both** sides:

- `app/src/test/kotlin/org/fossify/gallery/Poly1305AesVectorsTest.kt`
- `tools/fossify-cipher-cli/test_poly1305_aes.py`

The CLI computes the MAC with **pycryptodome** (`Poly1305.new(key=..., cipher=AES, nonce=...)`); no hand-written MAC implementation remains.

### 2.2 Container Format Contract (`helpers/vault/`)

The on-disk container format is defined in exactly one place, `app/src/main/kotlin/org/fossify/gallery/helpers/vault/`:

| File | Responsibility |
| :--- | :--- |
| `VaultContainer.kt` | Magic bytes, versions, IV/tag lengths, `payloadOffset()`, version/MAC lookup, content-IV validation |
| `VaultKeyDerivation.kt` | Key-separation domains and `deriveSubkey()` (HMAC-SHA256) |
| `VaultContainerWriter.kt` | The **single write path** for containers (`writeContainer`, `rewriteContainer`, `rewriteHeaderInPlace`) |

v3 container layout:

```
offset  size  content
0       8     magic "FGVLTENC"
8       1     version (3)
9       12    header IV (AES-256-GCM)
21      4     encrypted header length (big-endian)
25      N     encrypted header (GCM ciphertext + 16-byte GCM tag)
25+N    16    content IV (AES-256-CTR initial counter)
41+N    M     encrypted payload (M = original file size)
41+N+M  16    Poly1305-AES MAC tag
```

**All three write paths funnel through `VaultContainerWriter`:** file→file encryption, stream→file encryption, and rename (which rewrites the header while copying the payload verbatim, without re-encrypting media bytes).

### 2.3 Cross-Implementation Test Fixtures

`tools/fossify-cipher-cli/make_fixtures.py` produces `.bin` containers with the CLI and stores them under `app/src/test/resources/fixtures/cli/`. `CliFixtureCompatibilityTest` then asserts that the Android app can read, authenticate and decrypt every one of them, and that tampered payloads / MAC tags / content IVs / headers are rejected. ### 2.4 Corruption & Bit-Rot Behaviour (v3 today, v4 in 1.20)

This is the complete contract for what happens when encrypted bytes change on disk — flash bit-rot, a bad USB sector, an interrupted write or external tampering. **Read this before touching any read/write path.** User-facing term remains **Encrypted Vault / Şifreli Kasa**. The design decisions and their rationale live in [ADR 0001](docs/adr/0001-tink-streaming-aead-migration.md).

#### 2.4.1 "Decryptable" is not the same as "authentic"

Normal viewing paths — thumbnail (`EncryptedGlideLoader`), photo (`PhotoFragment`), video (`EncryptedMediaDataSource`), dimensions (`MediaDimensions`) — call `openDecryptedContentStream` / the Tink seekable channel **without full-file verification**. `verifyFileIntegrity()` runs only on the strict data operations in §2.4.5. A file can therefore be *decryptable* (produces bytes) while *not authentic* (bytes differ from what was originally written).

#### 2.4.2 What one flipped bit does

| Bit location | v3 — AES-256-CTR + Poly1305 | v4 — Tink AES-GCM-HKDF streaming |
| :--- | :--- | :--- |
| **GCM header** (name, dates, thumbnail) | Header auth fails → `readMetadata()` returns null → file effectively unavailable | Same: header auth fails → metadata unavailable |
| **Payload ciphertext** | CTR turns it into exactly **one wrong plaintext bit**. Photo/video still decodes; the app displays it **silently** (invisible in a JPEG, one glitched frame in MP4). Only export / pre-wipe rejects it via Poly1305. | That **segment's GCM tag fails**. Reading that segment throws; other segments still decrypt. Playback runs to that point then errors; full-file verification rejects the whole file. |
| **Integrity tag only** | Payload decrypts correctly; verification fails | Payload decrypts but the segment tag fails → segment rejected |

The practical answers:

- A bit in the **header** → effectively unreadable in both formats.
- A **v3 payload** bit → **not** undecryptable; silent corruption.
- A **v4 payload** bit → only that **segment** is undecryptable, not the whole file. The file never vanishes because of a verification failure.
- v4 trades silent degradation for a **loud, localized** failure. Left unhandled, sequential playback would stop with an error at the bad segment (a small GIF may fail to display entirely). Seeking past it recovers the rest because segments decrypt independently — but Media3/Glide do not do this automatically.

#### 2.4.3 Adopted policy: tolerant display, strict data operations

| Path | Behaviour on authentication failure |
| :--- | :--- |
| Thumbnail / photo / video / GIF / SVG / dimensions | Wrap the read: substitute **zeros for that segment only**, reposition to the next segment boundary, and continue. Never write the substituted bytes back. Emit a corruption report (§2.4.4). |
| Conflict comparison, dedup, pre-wipe verification, encrypted-area rebuild | **Strict** — reject/skip. Unverifiable bytes are never treated as valid data or re-encrypted into a valid-looking file. |
| "Dosyanın şifresini çöz" (explicit user action) | Allowed as an *unverified best-effort* output (§2.4.6). |

Substituting zeros is safe for display: the decoder gets a known placeholder rather than attacker-chosen plaintext, and no write path consumes the decoded stream.

#### 2.4.4 How the user learns about it

- Detection occurs in the read layer on background threads and can fire on every read, seek or thumbnail regeneration. It must **never** open a dialog there.
- A record is written to the app-private Room table `vault_corruption_reports`, keyed by (vault-relative path + file fingerprint), holding `firstDetectedAt`, `lastDetectedAt`, `badSegmentCount`, `notified`, `derivedFromCorrupt`. No cleartext sidecar file is placed in the Encrypted Vault.
- **Grid / album list:** small **yellow `!` overlay** on the thumbnail — the primary indicator, visible without opening the file.
- **Fullscreen viewer:** small yellow `!` badge in a corner; tapping it opens the dialog in §2.4.6.
- **First detection only:** one non-blocking toast/snackbar. Later detections only refresh `lastDetectedAt` — the warning never repeats on every appearance or seek.
- Records survive restarts. They are cleared when the `.bin` is deleted, securely wiped, or replaced by a verified re-encryption (fingerprint change); renames follow the existing path-update plumbing. When "Dosyanın şifresini çöz" writes a plaintext output, that path is recorded with `derivedFromCorrupt = true` so the badge and the hidden Move action follow the decrypted file too.
- **No quarantine and no automatic hiding** of damaged files.

#### 2.4.5 Which operations are strict

| Operation | Behaviour on a corrupted file |
| :--- | :--- |
| Normal export (`decryptFileToDirectory`) | Shows the dialog (§2.4.6); if cancelled, returns `null`. No plaintext is written and the `.bin` is untouched. |
| Copy | **Allowed.** Payload is copied verbatim, no tag is recomputed; the corruption record and badge follow the copy. |
| **Move** | **Action hidden entirely** for corrupted files — both encrypted and decrypted states. It is functionally identical to copy, so no Move entry and no explanatory notice. |
| Conflict / dedup comparison | `SOURCE_MAC_INVALID`: the file is never treated as bit-identical, so it cannot be auto-deduplicated or merged as an identical copy. |
| Pre-wipe verification (before wiping a plaintext source during a new encryption) | Returns `false`; the plaintext is not accepted as a verified duplicate. This is a direct gain of MAC verification: without it you cannot distinguish "damaged" from "valid but unusual media" and could write garbage while deleting the only surviving copy. Note this is **not** about forbidding deletion of a file — deleting a `.bin` is always allowed. |
| Rename | **Allowed.** The header-only rewrite copies the payload verbatim (v3 MAC covers payload only; v4 payload is bound to the immutable `fileId`), so renaming cannot launder the damage. The badge persists. |
| Deleting the `.bin` itself | **Always allowed**, including secure wipe. No integrity check gates deletion. |
| Encrypted-area rebuild | Skipped, left in v3, recorded as failed (§2.4.7). |

Three invariants make the relaxed operations safe: **(1)** no authentication tag is ever recomputed over damaged bytes; **(2)** no source is deleted on the strength of an unverified copy; **(3)** no dedup/conflict decision is made from unverified bytes.

#### 2.4.6 The corruption dialog and "Dosyanın şifresini çöz"

Shown identically in v3 and v4:

> "Dosyanın bazı kısımları doğrulanamadı. Dosyanızda veri kaybı oluşmuş olabilir. Dosyanızın başka bir yedeği varsa geri yükleyebilirsiniz ya da orijinal dosya internette yer alıyorsa mevcut dosyanızın şifresini çözüp web aratması yapabilirsiniz."

| Entry point | Left button | Right button |
| :--- | :--- | :--- |
| Yellow `!` badge / file menu | "Dosyanın şifresini çöz" | **Tamam** (default) |
| Normal export icon | **İptal** | "Dosyanın şifresini çöz" (primary) |

"Dosyanın şifresini çöz" reuses the existing decrypt function with `allowUnverified = true`. It streams through the tolerant reader, **keeps the encrypted source** (`deleteEncryptedSource = false`), and its output is never fed back into dedup, conflict checks, pre-wipe verification or re-encryption. There is **no "recovered / kurtarılmış" wording anywhere** — nothing was recovered, the output is still visibly damaged. It is a best-effort chance to reverse-search the intact portion online (works well for JPEG; for MP4 it depends on whether the damage landed in `mdat` or `moov`). The UI makes no promises.

**Repair is cryptographically impossible:** the original bits of a damaged segment are information-theoretically gone from the ciphertext. Only a backup — **if one exists** — can restore them; never assume the user has one.

#### 2.4.7 Unverifiable files during the opt-in rebuild

If full verification fails while the user rebuilds an older Encrypted Vault (§5, ADR §7), the file is **skipped and left byte-for-byte in v3** with a reason recorded; its temporary v4 file is deleted. Re-encrypting unverifiable data would produce a v4 file with a **valid tag over corrupted plaintext** — laundering the damage into something permanently undetectable — so it is refused. The vault still flips to v4 (the VMK is retained in the keyring so the leftover v3 files remain readable). The final report says *"N files could not be converted and remain in the old format; they are still accessible"*, and a **Retry failed** action can re-attempt them after the user restores the source. A mass failure (wrong key or wrong Encrypted Vault) aborts the whole rebuild instead of marking every file as failed.

#### 2.4.8 Why this is engineered this way

Bit-rot on phone eMMC/UFS is **rare** — ECC handles normal errors — and is more plausible on cheap USB/SD media, after unsafe removal, interrupted writes or power loss, which is exactly the external Encrypted Vault use case. The design assumes corruption is *exceptional*: it detects it loudly, keeps the user's media playable, and never silently propagates or "launters" damaged bytes.

A plain **move** is already trace-free when source and target share a filesystem — `rename(2)` changes only the directory entry, and the app uses this for atomic temp-file replacement. Encryption/decryption are *transformations*, not moves: two different byte sequences must coexist until the new one is verified, which is what preserves the only good copy if the process is interrupted. In-place CTR overwrite is technically possible but non-atomic (a crash leaves half-plaintext/half-ciphertext with no original), and external vaults are usually on a different filesystem where `rename` degrades to copy+delete anyway. "Forensic trace-free deletion" is not achievable at app level on flash (FTL wear-leveling, journal metadata); CSPRNG overwrite + `fsync` remains best effort as stated in §2.

### 2.5 Tink segment size — measurement and rationale (ADR 0001 §11.1)

v4 payloads are encrypted with Tink `AES256_GCM_HKDF`, which authenticates data in **segments**. The segment size is a write-time parameter; it is stored inside each encrypted header, and readers use the stored value. Four values are accepted: **16 / 64 / 256 KiB and 1 MiB** (Tink's default). The writer default is currently **256 KiB**.

#### Why the size matters

- **Sequential throughput:** every segment has its own GCM tag and IV setup, so more segments mean more per-segment work. Smaller segments are slower.
- **Seek latency:** to read byte X the reader must decrypt the whole segment containing X. Smaller segments mean less work per seek.
- **Tag overhead:** 16 bytes per segment. 256 KiB costs 0.006 %; 1 MiB costs 0.0015 % — negligible either way.
- **Corruption blast radius:** a single flipped bit invalidates that segment's tag. With the tolerant-display policy (§2.4.3), a smaller segment produces a smaller visible glitch. This is a side benefit, **not** the deciding factor.

#### Measurement 1 — JVM relative benchmark

`app/src/test/kotlin/.../V4SegmentBenchmark.kt`, opt-in so it never slows normal test runs:

```powershell
$env:CIPHER_BENCHMARK = "1"
.\gradlew.bat :app:testFossDebugUnitTest --tests "*V4SegmentBenchmark"
```

It encrypts a 128 MiB synthetic file at each candidate size, then measures sequential decrypt (median of 3 runs), and mean/p95 latency of 50 random seeks. Result on the development machine:

| Segment | Tag overhead | Sequential MiB/s | Seek mean ms | Seek p95 ms |
| :--- | :--- | :--- | :--- | :--- |
| 16 KiB | 0.098 % | 343.2 | 0.093 | 0.131 |
| 64 KiB | 0.024 % | 507.0 | 0.121 | 0.213 |
| **256 KiB** | 0.006 % | **564.2** | **0.388** | **0.500** |
| 1 MiB | 0.0015 % | 610.5 | 1.502 | 1.954 |

**Decision rule:** choose the *smallest* segment whose sequential throughput is within ~10 % of the best measured value, provided seek p95 stays below one frame budget (~16 ms). Best = 610.5 MiB/s; 90 % = 549.5. 16 and 64 KiB fall below; **256 KiB (564.2) is the smallest that qualifies**, with seek p95 0.5 ms. Hence 256 KiB — not Tink's 1 MiB default.

This is a **relative**, same-machine measurement, not a phone result.

#### Measurement 2 — real read pattern on a device (still required)

`MediaReadPatternProbe` (§2.4) records Media3's actual `read()` sizes, open/seek counts and bytes transferred. It is **always enabled in debug builds** — no `adb shell setprop` is needed (custom `cipher.*` properties are rejected by SELinux on many devices with "see dmesg for error reason"). Release builds require `cipher.measure_reads=1`.

Procedure:

1. Build a debug APK from the current source:
   ```powershell
   .\gradlew.bat :app:assembleFossDebug
   ```
2. Install it (uninstall the previous APK first if signatures differ — vault files on shared storage survive, but app-private settings do not):
   ```powershell
   adb install -r app\build\outputs\apk\foss\debug\gallery-39-foss-debug.apk
   ```
3. Clear the log, then in the app unlock the Encrypted Vault, open a **v4 encrypted video** and scrub forward/backward several times. **Exit the player** — the probe logs on `DataSource.close()`.
   ```powershell
   adb logcat -c
   adb logcat -s CipherReadProbe
   ```
   Example line: `CipherReadProbe: opens=2 seeks=7 reads=1432 bytes=31876608 128B..256B=4% ... >=64K=62%`

Interpretation: if reads are consistently ≥256 KiB and well aligned, 1 MiB may be reconsidered for slightly better sequential throughput; if they are small and randomly distributed, keep 256 KiB. Any playback smoothness issue is investigated with this data before changing the constant — see §11.1 of ADR 0001.

#### Measurement 2 result — device probe (2026-11-17)

Collected from a debug build on a real device with a v3 encrypted video:

```
opens=7..10  seeks=6..9  reads=45,444..61,306  bytes=17.9..24.2 MB
1B..128B=11%  129B..256B=4%  257B..512B=15%  513B..1024B=7%
1025B..2048B=13%  2049B..4096B=15%  4097B..8192B=15%
8193B..16384B=13%  16385B..32768B=1%  >=64K=2%
```

**Interpretation:** ~400 bytes per read on average, ~98 % of reads below 64 KiB, and only one seek per open plus a few scrubs. Media3 issues small but mostly **contiguous** reads, so the segment size determines the latency spike when a boundary is crossed, not the average throughput. A 1 MiB segment would cause a single ~1 MB decrypt spike per boundary; 256 KiB causes smaller, more frequent spikes. Given a reported smoothness concern, **1 MiB is explicitly rejected and 256 KiB is confirmed** as the writer default.

> **Status:** **256 KiB is final.** Revisit only if a v4 file shows a reproducible regression that is demonstrably segment-boundary related. The probe data came from a v3 video, so it does not by itself explain any v4 playback behaviour.

#### v4 probe vs v3 probe (2026-11-17)

After switching to a newly created v4 vault, the same probe was run again:

| | v3 | v4 |
| :--- | :--- | :--- |
| reads (cumulative) | 45,444–61,306 | 14,445–21,418 |
| bytes (cumulative) | 17.9–24.2 MB | 25.2–36.8 MB |
| bytes per read | ~394 B | ~1.7 KB |
| reads ≥64 KiB | ~2 % | 0 % |

Tink's buffering coalesces Media3's many tiny reads into **fewer, larger** reads — roughly a 4× reduction in read calls. The tester reported that the earlier perceived stutter was gone (possibly partly perceptual). This supports keeping 256 KiB.

#### v4 writer status

Newly created Encrypted Vaults now write **version 4** containers (`.vault` v4 keyring + Tink streaming payload), including the stream-encryption path `encryptStreamToDirectory`. Existing v3 vaults are untouched and keep writing v3.

Vault-level metadata in v4 uses `FVSTR2:` records: a per-purpose `HKDF(KEK, purpose)` key and AES-256-GCM with `purpose` as AAD. Album names, stealth-album JSON, restore manifests and resume blobs use distinct purposes, preventing record swapping between categories. v3 vaults keep their `FVSTR1:` records.

**Interrupted update behaviour:** an interrupted rebuild is never silently resumed. On the next vault unlock a single dialog states that the update was interrupted, that some files were converted, that **no data was lost**, and asks whether to continue. The "always ask" setting is forced back to ON after every interruption so the user cannot miss it. The in-app progress screen is modal, keeps the screen on, and shows the persistent "do not exit / do not turn off the screen" warning.

The application transitions through three distinct operational states to balance convenience and privacy:

```
                  ┌────────────────────────────────────────┐
                  │          MODE 1: Standard Mode         │
                  │   (Normal Albums, Vaults Locked)       │
                  └───────────────────┬────────────────────┘
                                      │ Enter Password /
                                      │ 3x Bottom Scroll
                                      ▼
                  ┌────────────────────────────────────────┐
                  │          MODE 2: Secret Vault          │
                  │  (Isolated View: Encrypted Physical    │
                  │     & Stealth Virtual Albums Only)     │
                  └───────────────┬────────▲───────────────┘
                         Back Key │        │ 3x Bottom
                                  │        │ Scroll Gesture
                                  ▼        │
                  ┌────────────────────────┴───────────────┐
                  │          MODE 3: Extended View         │
                  │  (Unified Grid: Standard Albums +      │
                  │    .nomedia Folders + Vault Folders)   │
                  └───────────────────┬────────────────────┘
                                      │ Swipe-kill App /

```

### 🔹 Mode 1: Standard / Locked Mode (Default)
- The state upon cold app startup when credentials have not been entered.
- System `.nomedia` directories (e.g., WhatsApp Stickers, app thumbnails) and encrypted vault folders under `Secrets` are **completely hidden**.
- Only unencrypted physical albums and standard virtual albums appear in the gallery grid.

### 🔹 Mode 2: Secret Vault Mode
- Activated by entering the vault password in Settings or performing a **3x bottom overscroll gesture** at the bottom of the main gallery list.
- **Isolated Vault View:** Standard photos and normal albums are completely filtered out. The user is presented with a dedicated vault screen containing **only encrypted physical albums and stealth virtual albums**.
- Action bars update to indicate active Secret Vault mode.
- **Encrypted Vault Recycle Bin:**
  - In Mode 2, deleted encrypted files are sent to a dedicated **Encrypted Vault Recycle Bin** inside `Secrets/` (unless permanent delete or skip recycle bin is selected).
  - Like all other vaults in `Secrets/`, its on-disk subfolder name is fully obfuscated (random 6-character hex identifier, e.g. `e8d2a1/`), protected with `.nomedia`, and its folder title is encrypted with `AES-256-GCM` in `.meta` as `$$VAULT_RECYCLE_BIN$$` (localized dynamically to "Recycle Bin" in memory).
  - Original folder locations are preserved in an encrypted `.restore_info` manifest (`AES-256-GCM`). Restoring items returns `.bin` files to their original parent vault subfolders (with auto-fallback to an active vault folder if the original directory was deleted).
  - Permanent deletion performs a secure CSPRNG wipe (`CryptoManager.secureWipeAndDeleteFile`) with 1 MiB block overwrites, truncation, and `fsync`.
  - Appears in the directory grid at position 0 (or bottom if "Show recycle bin last" is enabled) only when non-empty (`mediaCnt > 0`). Automatically hidden when empty or when outside Mode 2.
  - Fully compatible with the *"Always skip delete confirmation dialog"* preference (configured in the deletion dialog remember checkbox or under **Settings > File operations**).

### 🔹 Mode 3: Extended / Unified View Mode
- Activated when the user presses the **Android Back button** while inside Mode 2 (Secret Vault).
- The user returns to the primary gallery grid; however, normal albums, system `.nomedia` folders, and decrypted vault albums are displayed **together in a single unified view**.
- Performing the **3x bottom overscroll gesture** while in Mode 3 instantly transitions the user back into the isolated **Mode 2 (Secret Vault)**.
- **Unified Copy / Move Directory Picker (Mode 2 & Mode 3):**
  - When hidden items are unlocked, destination folder selection dialogs (`PickDirectoryDialog`) display **all three folder categories**:
    1. **Standard non-hidden directories** (Camera, Pictures, Downloads, etc.)
    2. **Unencrypted hidden directories** (folders with `.nomedia` or starting with `.`)
    3. **Encrypted hidden vaults** (physical vaults under `Secrets/` with decrypted names)
    4. *(If copying)* All virtual albums, no matter which physical folder the source files live in.
  - Safeguards ensure recycle bins are excluded from destination pickers, and Android 11+ SAF path restrictions are bypassed for internal encrypted vault directories.

### 🛑 Lock & Memory Zeroization (RAM Purge)
- When the user closes the app (swiping away from Android's Recents overview) or taps *"Stop showing hidden items"*:
  - The app locks immediately and returns to Mode 1.
  - In-memory Master Keys and cached file keys are zeroized (`fill(0)`).
  - Glide memory and disk caches are wiped to ensure decrypted frames do not persist in flash storage.

## 4. Virtual Album Rules & File Identity

**Core model — an album is bound to the file, not to its folder.** A virtual album does not own a
directory and never copies media. Each entry in `virtual_album_items` is a *direct relationship*
between the album and one specific file, described by that file's content and folder identity
(`MediaIdentity` + `FolderIdentity`, see item 4 below). The stored `full_path` and `parent_path`
are only a **cache of where that file currently lives** and are intentionally treated as mutable.

This distinction is the source of every rule in this section:

```text
  virtual album  ──(identity: mediaStoreId / size / fingerprint / folder inode+anchors)──▶  FILE
        │                                                                                     │
        └── cached full_path ──▶ /Pictures/Trip/IMG_1042.jpg   (may become stale after a move) ──┘
```

Because the relationship points at the file itself, the album survives everything that changes
the file's *address*: a rename, a move to a different real album, a move across storage volumes,
an encrypt/decrypt round trip, or a restore from the Recycle Bin. The resolver re-finds the same
file and rewrites the cached path; it never needs the user to re-add the file. Conversely, when
the file is genuinely gone (permanent deletion), the relationship is removed outright and a
same-named file appearing later at the old path is a *different* file, so it is not re-linked
(items 2 and 3 below). The only thing that is deliberately not forgiving is identity: an
identical-looking copy elsewhere on disk is never substituted for the original.

This model also has a direct UI consequence: **when a file is opened from a virtual album, the
viewer must page through that album's members rather than the neighbours of the file's real
folder** (see item 6).

1. **Multi-Source Albums:**
   - A virtual album may hold items from **any number of physical folders**, exactly like the favorites do.
   - The folder the items came from is only remembered as a hint for the copy dialog. It never rejects new items, so a folder that was renamed or moved can no longer leave an album that refuses to accept any file.
   - The directory picker offers every virtual album as a copy destination, no matter which folder the source files live in.
2. **"Move" Action Disabled:**
   - Because virtual albums only reference media without altering disk locations, the "Move" action is removed from virtual albums; only non-destructive "Copy" operations are permitted.
3. **Copy Flows from Virtual Albums:**
   - Media cannot be copied from a virtual album to its own owning physical album (the media already exists there).
   - Creating a new virtual album during a copy flow remembers the source folder as a hint for later copy flows.
4. **File & Zero-Pollution Folder Identity Architecture (Room v16 / `MIGRATION_15_16`):**
   - **Design Principle:** Filesystem paths are treated strictly as a *mutable cache*. Every Favorite (`favorites` table) and virtual album item (`virtual_album_items` table) persists a two-tier identity descriptor and lifecycle `state` (`OK`, `UNRESOLVED`, `ENCRYPTED`, `DECRYPTED`) without ever writing hidden marker files (such as `.folder_id`) into shared user directories (**Zero-Pollution**):

   ```text
   ┌───────────────────────────────────────────────────────────────────────────┐
   │ 1. CAPTURE (MediaIdentity + FolderIdentity + FolderIdentity.CaptureSession)│
   │    • File:   mediaStoreId, size, lastModified, fingerprint (64KB head+tail)│
   │    • Folder: folderInode (Os.stat.st_ino), capturedAtSec,                  │
   │              folderSignature (up to 5 sorted sibling <size>:<sha256>)      │
   └───────────────────────────────────────┬───────────────────────────────────┘
                                           ▼
   ┌───────────────────────────────────────────────────────────────────────────┐
   │ 2. PERSISTENCE (Room v16 + Automatic JSON Backups)                        │
   │    • Room tables `favorites` & `virtual_album_items` (`state` lifecycle)  │
   │    • Backups: `favorites.json`, `<Album>.json`, `Secrets/JSON/`    │
   └───────────────────────────────────────┬───────────────────────────────────┘
                                           ▼
   ┌───────────────────────────────────────────────────────────────────────────┐
   │ 3. ORDERED RESOLUTION PIPELINE (MediaIdentityResolver + ResolutionSession)│
   │    Layer 0a: Cached hint path (if present & not in `excludedPaths`)        │
   │    Layer 0b: Session relocated-folder cache (+ up to 2 ancestor levels)    │
   │    Layer 1 : Authoritative `MediaStore._ID` (batched IN-200) + FP check    │
   │    Guard   : `allHintParentsExist` -> blocks cross-folder scan if source   │
   │              folder still exists (in-folder rename only)                   │
   │    Layer 1.5: MediaStore `SIZE` query (+ `DATE_ADDED`) -> FP confirm       │
   │    Layer 2 : Bounded filesystem fallback (depth<=4, stat<=15000, cap=40;   │
   │              scans standard + custom/external roots; skips `.vault` plain) │
   └───────────────────────────────────────┬───────────────────────────────────┘
                                           ▼
   ┌───────────────────────────────────────────────────────────────────────────┐
   │ 4. SCORING & CROSS-FOLDER CONTINUITY GATE (`selectBestCandidate`)         │
   │    • Filter out `excludedPaths` (already claimed live paths)               │
   │    • Require `hasPositiveContinuity` (rejects foreign & pre-existing copy) │
   │    • Deterministic precedence (`CandidateScore`):                          │
   │      ID > Inode > Sibling Anchors > Trailing Path > MTime > NameSim > Path │
   └───────────────────────────────────────────────────────────────────────────┘
   ```

   - **Two-Tier Identity Model (`MediaIdentity` & `FolderIdentity`):**

     | Tier | Fields | How It Works & Cost |
     | :--- | :--- | :--- |
     | **File Identity** (`MediaIdentity`) | `mediaStoreId`, `fileSize`, `lastModified`, `fingerprint` | `fingerprint` hashes the first 64 KB and last 64 KB via `SHA-256` (`O(1)` I/O regardless of video size). |
     | **Folder Identity** (`FolderIdentity`) | `folderInode`, `folderSignature`, `capturedAtSec` | Reads `Os.stat(parent).st_ino` plus up to `5` sorted non-hidden sibling `<size>:<sha256>` anchor tokens (excluding the item itself; directory child scan capped at `2000`). `CaptureSession` caches directory metadata per batch so bulk operations hash sibling anchors once per folder. |

   - **Persistence, Dormant Encrypt/Decrypt Trace Preservation & Explicit Deletion (`GalleryDatabase` v16 & JSON Sync):**
     - `FavoritesDao.updateFavoriteIdentity` and `VirtualAlbumsDao.updateItemIdentity` update relocated paths and file identity while preserving existing non-zero/non-empty `folder_inode`, `folder_signature`, and `captured_at_sec` values.
     - Both `ReferenceBackupManager` (`favorites.json`) and `VirtualAlbumSyncManager` (`Virtual Album Saves/*.json` and encrypted `Secrets/JSON/*.json` manifests) serialize all folder identity columns and dormant lifecycle states (`ENCRYPTED`, `DECRYPTED`) with backward-compatible defaults. For encrypted `Secrets/JSON/fva_<hash>.json` manifests, `VirtualAlbumSyncManager` also stores vault-relative descriptors (`relativeVaultPath` / `relativeParentVaultPath`) alongside `fullPath` so `syncVirtualAlbums` automatically remaps Room DB paths across external vault remounts (see [Section 5](#5-device-migration-backup--vault-auto-detection)).
     - **Dormant Encrypt <-> Decrypt Lifecycle (`markReferencesOnEncrypt` / `markReferencesOnDecrypt`):**
       - Encrypting a plaintext album or file into the vault wipes MediaStore/thumbnail/mediaDB traces (`purgeMediaTracesPreservingReferences`) while transitioning matching active **Favorites** and **public Virtual Album** entries to dormant `ITEM_STATE_ENCRYPTED` (hidden from gallery UI, ZIP exports, and relocation scans). Decrypting that file back to plaintext—even into a different folder—automatically restores those references to `ITEM_STATE_OK`.
       - Symmetrically, decrypting an encrypted `.bin` referenced by a **Stealth Virtual Album** (`isHidden = true`) stores the plaintext `(fileSize, lastModified, fingerprint)` and marks the entry `ITEM_STATE_DECRYPTED` (hidden while unencrypted). Re-encrypting the album or file reconnects the entry to the brand-new randomized `.bin` filename and IV under `ITEM_STATE_OK`.
     - **Explicit Deletion, Recycle Bin Exception & Irreversible Removal (`deleteDBPath`, `deleteDBPaths`, `emptyTheRecycleBin`, `restoreReferencesAfterRecycleBinRestore`, `References`):**
       - *Recycle Bin Exception (Standard & Vault):* Deleting a file or physical album while Recycle Bin is active keeps its Favorites (`media.deleted_ts != 0` filter) and Virtual Album references hidden (excluding both Recycle Bin paths and `isVaultRecycleBinPath`) until restored; restoring from Recycle Bin (`restoreRecycleBinPaths`, `restoreVaultRecycleBinFiles`) brings references back immediately (updating paths via `restoreReferencesAfterRecycleBinRestore` if the restored filename/folder changed).
       - *Irreversible Permanent Deletion:* Permanently deleting a physical album or item (Recycle Bin off, Skip Recycle Bin in `MainActivity`/`MediaActivity`/`ViewPagerActivity`, emptying Recycle Bin / Vault Recycle Bin, or an external deletion confirmed on a mounted, readable storage volume when a full `allowFilesystemFallback = true` repair pass finds no moved copy) removes references permanently from **both** Virtual Albums and Favorites as well as `favorites.json` / `<Album>.json` / `JSON/fva_*.json`. Creating a brand-new folder or re-uploading a same-named file at that path later will never resurrect deleted references.
       - *Temporary Unmount Safety:* If the storage volume is unmounted (`!isStorageVolumeMountedAndReadable`) or an encrypted vault is locked, missing items stay `UNRESOLVED` until the volume or vault returns. Moved albums outside standard roots (`DCIM`, `Pictures`, etc.) or on external volumes are scanned by Layer 2 (`MAX_FALLBACK_FILES_VISITED = 15000`), while `.vault` subtrees are excluded during plaintext searches.
   - **Same-Filename Isolation, Two-Pass Batch Repair & Duplicate Ranking:**
     - Database uniqueness constraints and membership checks operate on full paths (`full_path` / `(album_id, full_path)`), not display filenames. Having files with the same name in different folders (e.g., `Pictures/A/photo.jpg` and `Pictures/B/photo.jpg`) never causes adding one to match, display, or duplicate the other.
     - Batch repair uses a shared `ResolutionSession` across two passes (`allowAmbiguous = false`, then `allowAmbiguous = true`):
       - **Pass 1 (`allowAmbiguous = false`):** Unambiguous items (including `MediaStore._ID` moves and items uniquely proven by `folderInode` / sibling anchors) resolve immediately and populate the session's relocated-folder map (`recordRelocation`, covering the parent folder and up to `2` matching ancestor directory levels). Items with genuinely ambiguous duplicates defer.
       - **Pass 2 (`allowAmbiguous = true`):** Remaining duplicate entries hit **Layer 0b** in `O(1)` when a sibling revealed the destination folder, or evaluate `selectBestCandidate` after excluding already claimed live paths (`excludedPaths`).
     - Verified candidates passing the continuity gate are ranked strictly by `CandidateScore`:
       1. `exactMediaStoreId` (`MediaStore._ID` match)
       2. `inodeMatches` (parent directory `st_ino` match)
       3. `matchedAnchorCount` (count of matching sibling `<size>:<sha256>` anchors)
       4. `trailingFolderMatches` (longest shared trailing path segments)
       5. `lastModifiedMatch` (exact millisecond mtime match)
       6. `folderNameSimilarity` (token-aware similarity with word-boundary guards)
       7. `commonPrefixSegments` -> `exactFileNameMatch` -> shortest normalized path.
   - **Existing-Folder, Deleted-Folder & Pre-Existing Foreign Copy Protections (`Pictures/A` vs `Pictures/B`):**
     - **Existing Source Folder Guard (`allHintParentsExist`):** If `Pictures/A` still exists on disk (e.g., `photo.jpg` was deleted or `Pictures/A` was emptied externally), Layers `1.5` (`SIZE` scan) and cross-folder Layer `2` are suppressed. Filesystem resolution inspects only `existingParentDirs` for in-folder file renames, guaranteeing that identical files in `Pictures/B` are never pulled.
     - **Deleted Source Folder & `hasPositiveContinuity` Gate:** If `Pictures/A` was deleted completely externally, candidates outside the hint path must prove positive continuity—at least one of `exactMediaStoreId`, `inExistingHintParent`, `inodeMatches`, `matchedAnchorCount > 0`, or `!isPreExistingForeignCopy && (trailingFolderMatches > 0 || folderNameSimilarity >= 50)`.
     - **Temporal Pre-Existing Foreign Copy Rejection:** Layer `1.5` projects `MediaStore.MediaColumns.DATE_ADDED`. A candidate in another folder with a different `MediaStore._ID` whose `dateAddedSec < capturedAtSec - 5` existed *before* the user created the reference and is disqualified as an independent foreign copy.
     - **Short-Name Boundary Guard:** `computeFolderNameSimilarity` enforces token boundaries and a minimum 3-character length for substring checks so short folder names like `A` never spuriously match unrelated names like `Archive`.
     - **Known Physical Edge Case:** If a standalone single-file `.nomedia`/unindexed folder with zero sibling anchors, no `MediaStore._ID`, and no preserved inode is renamed to a completely unrelated name *or* duplicated to a sibling folder before deletion, both states are indistinguishable on disk; the resolver prioritizes data safety and keeps the item `UNRESOLVED` rather than hijacking another folder's file.
5. **Non-Destructive Favorites Deletion:**
   - Deleting the Favorites virtual directory confirms with the same non-destructive prompt as virtual albums and clears only Favorites metadata and `favorites.json`, leaving original media files untouched in their physical folders.
6. **Viewer Album Context — Following the Album–File Relationship into the Full-Screen Viewer:**
   - Because the album is bound to the file and not to the file's folder, opening a member from a virtual album must keep the viewer inside **that album's membership list**. The neighbours shown while swiping, the per-album sort order, and the availability of the **Shuffle** action all belong to the album the file was opened from — never to the real directory the file happens to live in.
   - Album identity is passed explicitly as the `EXTRA_ALBUM_PATH` intent extra (`helpers/Constants.kt`). Every viewer launch site supplies it: the normal file tap and the slideshow in `MediaActivity`, the shortcuts created in `MediaActivity`/`MediaAdapter`, and the external-intent relay in `PhotoVideoActivity`. `ViewPagerActivity.initContinue` resolves `mDirectory` from this extra, so the fallback `mPath.getParentPath()` (the file's *real* parent) is only used for third-party intents that carry no album at all. Without this, a file whose cached path had been relocated by the identity resolver (item 4) would silently open "as if" it were still in its original physical album — showing that album's neighbours and hiding Shuffle because the wrong sort scope was read.
   - The "Show all folders content" flag is explicitly suppressed for virtual albums, both in `MediaActivity` (`mShowAll`) and in `ViewPagerActivity`. Otherwise the global media list would replace the album's own member list, again breaking the direct album–file relationship in the UI.
   - Shuffling a virtual album writes its order only into that album's `RandomOrderManager` scope. It no longer overwrites the global `SHOW_ALL` order or the process-wide `MediaActivity.mMedia` grid cache, which otherwise leaked the album's list into the next album that was opened.
   - This is strictly a viewer-context fix: reference repair, the two-pass ambiguous-duplicate resolution, and the identity-driven path rewrites described in item 4 are unchanged. Those mechanisms are precisely what keep the album connected to the file after a move, so limiting them would break rule 4.

## 5. Device Migration, Backup & Vault Auto-Detection

- **Portability:** To migrate vaults to a new phone or restore after a factory reset, copy the `Calypso Gallery` folder into the new device's internal storage root, or mount/connect your external USB drive or SD card containing `Secrets/` and select **Use existing vault** during vault setup (or via **Settings > Encrypted vault > Vault location**).
- **Automatic Backups:** Favorites (`Favorites/favorites.json`) and public virtual albums (`Virtual Album Saves/*.json`) are backed up inside `Internal Storage > Calypso Gallery` as they change, so clearing app data does not lose them and backups restore automatically on a clean start.
- **Strict Automatic Detection of Existing Internal Vaults (`CryptoManager.locateVaultRootOnDisk`):**
  - If `Internal Storage > Calypso Gallery > Secrets/.vault` (or an existing vault still under `.../Calypso Gallery/Cipher_Secrets`, a legacy internal path under `Documents/Cipher/Cipher_Secrets`, `Documents/Cipher_Secrets`, `Documents/Secrets`, `Documents/Cipher/Secrets`, `Documents/Cipher`, or an already-configured `config.vaultRootPath`) exists on disk—such as after reinstalling the app or restoring an internal backup—`CryptoManager.locateVaultRootOnDisk` detects it automatically and `openSecretVaultPrompt` / Settings unlocks it directly using your existing password, PIN, or pattern, **without** showing location-setup prompts. Upgrades never rename an existing `Cipher_Secrets` folder; legacy locations are only relocated into the standalone app container while keeping their original name.
  - **No Silent External Auto-Adoption:** When `config.vaultRootPath` is empty, `locateVaultRootOnDisk` checks **only** default and legacy internal locations; unconfigured external USB drives or SD cards are **never** silently bound without explicit user action. `CryptoManager.findCandidateExternalVaultRoots` (scanning `listExternalStorageVolumeRoots`, `sdCardPath`, and POSIX `config.OTGPath`) is used solely as a convenience default starting folder when the user browses to pick an existing vault.
- **Two-Stage Vault Setup & Selection Flow (`Activity.kt`, `VaultSecurityDialog.kt`, `SettingsActivity.kt`):**
  - When **no** vault exists at the default or configured location, triggering the vault (via the pull-to-open gesture `openSecretVaultPrompt`, encrypting files/albums, or **Settings > Encrypted vault > Create encrypted vault** / *"Şifreli kasa oluştur"*) launches `promptCreateVault` -> `promptVaultSetupChoice`:
    1. **Stage 1 (`promptVaultSetupChoice` — *"Encrypted vault"*):**
       - **`1) Create new vault`** (`create_new_vault_option` / *"Yeni kasa oluştur"*)
       - **`2) Use existing vault`** (`use_existing_vault_option` / *"Mevcut kasayı kullan"*)
    2. **`Use existing vault` Branch (`pickExistingVaultAndUnlock` -> `unlockCandidateVault`):**
       - Opens `FilePickerDialog` (`enforceStorageRestrictions = false`), pre-seeding the starting directory from `CryptoManager.findCandidateExternalVaultRoots` -> `config.vaultRootPath` -> `listExternalStorageVolumeRoots` -> `internalStoragePath`.
       - Uses `CryptoManager.resolveExistingVaultInDirectory` to check for a valid `.vault` header directly inside `<picked>`, `<picked>/Secrets`, `<picked>/Cipher_Secrets`, `<picked>/Calypso Gallery/Secrets`, `<picked>/Calypso Gallery/Cipher_Secrets`, `<picked>/Cipher/Secrets`, `<picked>/Cipher/Cipher_Secrets`, or the former app container. If found (and confirmed via `unlockCandidateVault`), it prompts for the vault password or PIN and **connects to and unlocks that existing vault** instead of overwriting it (`setupOrUpdateCredentialsInternal` explicitly guards against overwriting an existing `.vault`). If none is found, `showNoExistingVaultDialog` informs the user and lets them re-pick or go back.
       - Canceling or pressing **Back** at any step (`FilePickerDialog`, confirmation, or PIN/password unlock) rolls back via `VaultConfigSnapshot` + `CryptoManager.clearCachedVaultRoot()` and navigates cleanly back to the previous step.
    3. **`Create new vault` Branch -> Stage 2 (`promptWhereToCreateVault` — *"Where should the vault be created?"* / *"Kasa nerede oluşturulsun?"*):**
       - **`1) Default Location`** (`vault_location_default_short` / *"Varsayılan Konum"*): Creates `Internal Storage > Calypso Gallery > Secrets`.
       - **`2) Custom Location`** (`vault_location_custom_short` / *"Özel Konum"*): Opens `FilePickerDialog` (`pickCustomFolderForCreateVault`) and validates the chosen path via `validatePickedVaultDirectory` (never overwriting if a `.vault` already exists there; instead offering/routing to unlock the existing vault or returning to folder selection).
       - Followed by password/PIN creation in `VaultSecurityDialog`. Pressing **Back** or **Cancel** unwinds cleanly one step at a time (`VaultSecurityDialog` `onCancelCallback` -> `FilePickerDialog` dismiss listener -> Stage 2 `promptWhereToCreateVault` -> Stage 1 `promptVaultSetupChoice`).
- **USB OTG / External Path Resolution (`CryptoManager.resolvePickedPathToFile`):**
  - Rather than relying on Fossify's `isPathOnOTG(pickedPath)` check—which produced false-positive rejections on real POSIX-mounted `/storage/<UUID>/...` volumes whenever `MainActivity.checkOTGPath()` stored that mount path in `config.OTGPath`—`validatePickedVaultDirectory` delegates to `CryptoManager.resolvePickedPathToFile(context, pickedPath)`:
    - Direct POSIX paths are accepted directly.
    - `otg:` pseudo-paths are resolved via `config.OTGPartition` mount roots (`/storage/...`, `/mnt/media_rw/...`, `/mnt/runtime/write/...`, `/mnt/runtime/default/...`), `listExternalStorageVolumeRoots`, and SAF `DocumentFile` -> `/proc/self/fd` `Os.readlink`.
    - `content://` tree/document URIs are resolved via `/proc/self/fd` `Os.readlink` and `DocumentsContract` (`raw:`, `primary:`, or external volume ID).
    - After creating the directory if needed, `CryptoManager.canWriteToDirectory` verifies real POSIX file creation. Only when a device/ROM exposes USB OTG strictly as a virtual SAF provider without an accessible writable POSIX mount directory is `usb_direct_filesystem_required` shown.
- **Viewing or Switching Vault Location (`Settings > Encrypted vault > Vault location`):**
  - **Settings > Encrypted vault > Vault location** (`settings_vault_location_holder` / `SettingsActivity.setupVaultLocation`) displays the active vault root (`Standard (Internal Storage)`, the custom path, or `External drive disconnected (%s)`) and invokes `promptVaultSetupChoice(confirmBeforeCreatingNew = hasConfiguredVault)` so you can switch to another existing vault or initialize a new vault at any time (prompting confirmation before creating a brand-new vault at a different location).
  - Switching to another vault invokes `VirtualAlbumSyncManager.evictHiddenVirtualAlbumsFromDbCache(context)` (via `CryptoManager.prepareVaultLocationSwitch` and `unlockCandidateVault`), clearing only cached `isHidden = true` virtual album rows from Room DB without touching public virtual albums or deleting on-disk `Secrets/JSON/*.json` backups.
- **Vault-Relative Stealth Virtual Album Manifests (`VirtualAlbumSyncManager`, `VirtualAlbumsDao`):**
  - Encrypted `Secrets/JSON/fva_<hash>.json` manifests persist vault-relative `relativeVaultPath` (`VirtualAlbumItemBackup`) and `relativeParentVaultPath` (`VirtualAlbumBackup`) alongside `fullPath` (extracted by `extractRelativeVaultPath`, normalizing `\` to `/`, preferring the active `vaultRoot` prefix with `/Secrets/`, `/Cipher_Secrets/` and `/Cipher/` fallbacks for legacy manifests, ignoring `JSON/`, and rejecting `.` / `..` traversal segments).
  - When an external USB or SD vault mounts at a different path or UUID across sessions or devices, `syncVirtualAlbums` resolves each member via `resolveVaultItemPath` relative to the active `vaultRoot`, automatically rewrites stale Room DB paths (`VirtualAlbumsDao.updateItemPathInAlbum`, `updateAlbumParentPhysicalPath`), and re-saves the manifest cleanly. Desktop `tools/fossify-cipher-cli/cipher_vault.py` maintains strict separation and never reads or modifies `JSON/`.
- **Native External-to-Phone Vault Synchronization (`Settings > Encrypted vault > Sync vault from external drive`):**
  - Users who keep their primary `Secrets` vault on internal phone storage while encrypting media on Tails OS onto USB/SD drives can merge external ciphertext directly inside the unlocked Android app via **Settings > Encrypted vault > Sync vault from external drive** (*"Harici diskten kasayı eşitle"*, `settings_sync_vault_holder` -> `SettingsActivity.setupSyncVault` -> `Activity.promptSyncVaultFromExternal` -> `CryptoManager.syncVaultFromExternalDirectory`).
  - **Unified `Secrets` USB Layout & Read-Only Mount Support:** `promptSyncVaultFromExternal` passes `requireWritable = false` to `validatePickedVaultDirectory` so read-only external USB/SD mounts can be synced cleanly (`vault_location_not_readable` if unreadable). Both Tails OS USB setups work identically under `<USB>/Secrets/`:
    1. **Full external `Secrets` copy on USB:** Holds `.vault` plus existing `<hex>/.meta` folders updated by `cipher_vault.py`.
    2. **Header-only `<USB>/Secrets/.vault` (zero media mirror on USB):** Holds only the small `.vault` key-header file (or `<USB>/.vault`, which `choose_encrypt_output_dir` auto-targets to `<USB>/Secrets/`), receiving only newly encrypted `.meta` subfolders and `.bin` files. *(Explicit `-o` directories or Desktop fallback `Encrypted_Output` / `Sifreli_Cikti` are also supported.)*
  - **Flexible Source Resolution (`CryptoManager.resolveSyncSourceRoot`):** Normalizes the selected folder—whether you pick `<USB>/Secrets`, a USB drive root holding `Secrets` / `Cipher_Secrets` / `Calypso Gallery/Secrets` / `Calypso Gallery/Cipher_Secrets` / `Cipher/Secrets` / `Cipher/Cipher_Secrets` / `Encrypted_Output` / `Sifreli_Cikti`, a single `.meta` album folder (`hasFolderMetaFile`), or a flat folder of bare `.bin` files. Rejects self-sync against the active phone vault (`vault_sync_same_folder_error`).
  - **Automatic Album Routing & Lazy Integrity-Guarded Creation:**
    - Bare root `.bin` files and subdirectories whose decrypted `.meta` name satisfies `isDefaultAlbumRawName` route to the phone vault's **Default Secret Album** (`getOrCreateDefaultHiddenAlbum`).
    - Named `.meta` or plain subdirectories match existing destination encrypted albums (exact decrypted `.meta` name first, then trimmed case-insensitive match via `matchExistingDestinationAlbum`) or **lazily create** a new 6-character hex encrypted album (`createHiddenPhysicalAlbum`) only after an incoming `.bin` passes `readMetadata` and `Poly1305-AES` `verifyFileIntegrity` (preventing empty orphan folders when corrupt or foreign-key files fail).
    - `JSON/`, `$$VAULT_RECYCLE_BIN$$` (`VAULT_RECYCLE_BIN_NAME`), and dot-prefixed folders without `.meta` are ignored. Source files remain untouched on external media; writes stream to `.sync_tmp_*.bin`, flush via `fd.sync()`, and atomically move into place.
  - **Incremental `.pending_sync` Manifest (`CryptoManager.PENDING_SYNC_FILE_NAME`):** When encrypting new media into `Secrets`, `cipher_vault.py` appends relative `.bin` paths to `Secrets/.pending_sync`. `syncVaultFromExternalDirectory(..., requirePendingManifest = true)` strictly reads only those pending entries (refusing to scan the whole archive when `.pending_sync` is absent or empty), clears succeeded entries, retains only failed entries, and deletes `.pending_sync` once empty—preventing repeated re-scans and unrelated archive bit-rot failures. Future desktop clients must track their own independent pending-sync manifest so phone and desktop sync states do not interfere.
  - **Album Encryption / Decryption Conflict Resolution (`AlbumCryptoConflictDialog`, `ALBUM_CRYPTO_CONFLICT_MODE`, `EncryptConfirmationDialog`):**
    - Encrypt and Decrypt confirmation dialogs include an inline `i` info button explaining folder/file encryption, album renaming vs. merging, and conflict rules.
    - When encrypting or decrypting an album whose name already exists at the destination, `resolveAlbumCryptoOptions` honors **Settings > File operations > Album conflict (Encrypt / Decrypt)** (`Always ask` default, `Merge into existing album`, `Merge into existing album and auto-delete identical sources`, or `Create new album as (1)`).
    - Choosing `Create new album as (1)` creates `<Album>(1)`, `<Album>(2)`, etc. without modifying existing albums; choosing `Merge into existing album` prompts once per batch whether 100% bit-identical + timestamp-equivalent source files should be deleted or kept, while `Merge into existing album and auto-delete identical sources` (`ALBUM_CRYPTO_CONFLICT_MERGE_DELETE_IDENTICAL`) deletes matching identical source files automatically without a prompt.
  - **Single-Pass Sync Optimization, Cached Indexes & Optional Fast Large-File Check (`CryptoManager.syncVaultFromExternalDirectory`, `CopyMoveHelper`, `SettingsActivity`):**
    - **Cached Target Directory Indexes (`TargetPlainIndex` & `TargetEncryptedIndex`):** Both external vault sync and Copy/Move/Encrypt/Decrypt batch operations cache destination directory listings and AES-GCM metadata headers in memory once per folder rather than re-scanning directories and re-decrypting headers per file. Batch folder encrypt/decrypt operations pass `preExistingPaths` snapshots so siblings in the same source folder (`photo.jpg` and `photo(1).jpg`) cannot deduplicate against one another mid-batch.
    - **Stage 0 (`O(1)` Mirrored `.bin` Fast-Skip):** Inside an already-existing destination album, `albumBinNameIndex` checks for same-named `.bin` files and invokes `hasMatchingMacTrailer(sourceBin, matchingMirrorBin)`—verifying matching byte length, authenticated container header (`isMacAuthenticatedContainerHeader`: `MAGIC_V2`/`MAGIC_V1` + authenticated version byte), and trailing 16-byte `MAC_TAG_LENGTH` Poly1305 tag (`trailingMacTagsEqual`). Unchanged mirror files skip in `O(1)` seeks without decrypting AES-GCM headers or hashing gigabytes of video.
    - **Stage 1 (Authenticated Header Filter & Symmetric Collision Family):** Resolves `originalName`, `lastModified`, and `dateTaken` via cached headers and filters collision candidates via symmetric `isSameOrCollisionVariant` (`<stem>(k)<ext>`). Distinct filenames skip payload comparison and stream-copy + MAC-verify in a **single I/O pass** (`copyBinAndVerifyIntegritySinglePass`).
    - **Stage 2 (`O(1)` `contentIv` + MAC + Timestamp Duplicate Check):** Requires `areEncryptedTimestampsEquivalent(sourceMeta, existingMeta)` alongside `isFastMacMatchDuplicate` (`originalSize > 0L`, `mediaType`, `file.length()`, `contentIv`, `isMacAuthenticated`, payload bounds, and `trailingMacTagsEqual`) before skipping.
    - **Stage 3/4 (Single-Pass Source MAC + Content Comparison + Timestamp Equivalence):** Filters to candidates matching `originalSize`, `mediaType`, **and** `areEncryptedTimestampsEquivalent`, then runs `compareEncryptedStreamAndVerifySourceMac` in a **single pass** using `64 KB` buffers (or 5 `256 KB` samples when fast large-file check is explicitly enabled). Two files are deduplicated (`skippedDuplicateCount`) **only** when both payload bits and timestamps match (within the `2,000 ms` FAT32/MediaStore tolerance); a re-uploaded bit-identical file with a different timestamp bypasses duplicate-skip and is preserved via `<name>(1)`.
  - **Conflict-Safe `<name>(1)` Renaming (`formatCollisionFileName` + `CryptoManager.renameEncryptedFile`):** Same-named files with differing plaintext bits **or** differing timestamps in the same target album (including Default Secret Album) are imported and renamed inside their encrypted header to `<stem>(1)<ext>`, `<stem>(2)<ext>`, etc., never overwriting or shadowing existing media. Reports `VaultSyncResult` (`copiedCount`, `renamedCount`, `skippedDuplicateCount`, `failedCount`, `syncedAlbumsCount`). For the full **Bit-to-Bit + Metadata Equivalence Architecture** and timestamp guarantees, see [Section 10](#10-timestamp-preservation-lastmodified--datetaken--metadata-risks).
- **Destructive Vault Reset Protection (`DeleteCipherSecretsDialog`):** Tapping **Empty encrypted vault** runs a mandatory 10-second countdown, requires ticking an explicit confirmation checkbox after the timer expires, and positions the "Yes" button on the left to prevent accidental muscle-memory taps. When a custom vault path is configured, `CryptoManager.deleteExistingVault` scopes deletion strictly to the active custom vault rather than touching unrelated default internal directories.
- **External Vault Unplug Protection (`isConfiguredVaultTemporarilyUnavailable`):**
  - If a configured custom vault resides on an external USB drive or SD card (outside internal storage) and the drive is temporarily disconnected, `CryptoManager.isConfiguredVaultTemporarilyUnavailable` detects the missing external volume.
  - `CryptoManager.verifyVaultOnDisk` locks the active RAM session (`lockVault()`), clears in-memory folder caches, and prompts the user with **External vault unavailable** (`promptUnavailableExternalVault` with **Retry**, **Change location**, and **Cancel**) **without** wiping `config.vaultRootPath`, wrapped key state (`vaultWrappedKeyData`, `vaultPublicKey`), or biometric unlock state (`isVaultBiometricEnabled`, `vaultBiometricWrappedBundle`).
  - Once the external drive or SD card is plugged back in, tapping **Retry** or reopening the vault automatically locates the vault at `config.vaultRootPath` and resumes normal unlocking (including biometric unlock if enrolled).

## 7. Zero-Disk Offline Lockdown & Removed Network Features (`1.18.0-cipher`)

> [!IMPORTANT]
> Starting in **1.18.0-cipher**, all in-app network capabilities—including **Direct URL Sharing (`VaultShareActivity` / `VaultDownloader`)** and the **In-App Vault Browser (`VaultWebViewActivity`)**—have been permanently removed from Calypso Gallery, and `android.permission.INTERNET` is stripped via `tools:node="remove"` in `AndroidManifest.xml` alongside code-level blockers in `App.kt` and `SvgModule.kt`.
>
> **Why:** Android grants `INTERNET` per Linux UID (whole APK), not per Activity. Because a media gallery bundles numerous third-party and native media decoders, keeping `INTERNET` inside the gallery APK leaves a theoretical supply-chain exfiltration vector. By making the gallery **100% offline at the kernel UID boundary**, no library or dependency can transmit gallery media over the network.
>
> **Recommended Ingestion & Roadmap:**
> - **Offline Desktop CLI (Recommended):** Run `tools/fossify-cipher-cli/run.sh` (`cipher_vault.py`) inside a RAM-only live-boot Linux OS such as **Tails OS** (or a `toram noswap` Live ISO) in **Encrypt-Only** mode to encrypt plaintext files from RAM directly into `<USB>/Secrets/` (using either a full vault copy or only your `.vault` header file), which can then be played directly from external storage or merged into a phone vault via **Sync vault from external drive** (and remains compatible with a planned RAM-only desktop viewer).
> - **Standalone External WebView Browser (In Development):** For direct mobile encrypted downloads without a PC, an independent external WebView downloader application (separate APK / separate Linux UID) is currently being developed.

## 8. Offline Zero-Disk Media Ingestion (Desktop Linux CLI)

Calypso Gallery prioritizes **air-gapped offline encryption** so unencrypted plaintext files never touch mobile or desktop non-volatile storage and the gallery app itself remains 100% network-isolated:

| Option | Environment | Target Use Case | Security Model |
| :--- | :--- | :--- | :--- |
| **Desktop Linux CLI (Recommended)** | Desktop Linux ([tools/fossify-cipher-cli/](tools/fossify-cipher-cli/README.md)) — **Tails OS** or `toram noswap` Live ISO ideal | **Encrypt-Only** offline batch imports, direct external USB/SD vault encryption, unified `<USB>/Secrets` phone sync | Encrypts plaintext from volatile RAM (`tmpfs`) straight into unified `Secrets/` (or Desktop fallback `Encrypted_Output` / `Sifreli_Cikti`) with per-process `bubblewrap` (`bwrap`) network/disk isolation. Contains no decryption code; Gallery APK has zero network permissions. |
| **Standalone Mobile Browser APK (In Development)** | Separate Android APK (External WebView) | On-device encrypted downloads without a PC | Isolated Linux UID with `INTERNET` only; zero access to gallery storage or decryption keys. |

### Recommended Workflows: Tails OS (RAM-Only Live Boot) + Unified `Secrets` USB Drive

1. **Download / Stage Plaintext Media in Volatile RAM (`tmpfs`):**
   - Boot into **Tails OS** (or another Linux Live ISO with `toram noswap`, e.g., Debian Live `boot=live toram noswap`). `run.sh` checks `/proc/swaps` at startup and warns if any non-`zram` disk-backed swap partition is active (`sudo swapoff -a`).
   - Place plaintext media in `~/Desktop/To_Encrypt` (English, `--lang en`) or `~/Desktop/Sifrelenecek` (Turkish, `--lang tr`), which reside in volatile RAM (`tmpfs`).
2. **Mount the External USB / SD Drive Holding `Secrets/` (Full Vault OR `.vault`-Only):**
   - On the external USB/SD drive, create `Secrets/` and place inside it either a **full copy** of your vault or **only your small `.vault` header file** (or place `.vault` directly at `<USB>/.vault`, which automatically routes output to `<USB>/Secrets/`). `find_vault_file` prioritizes mounted vaults under `/media`, `/run/media`, `/mnt`, and `Persistent`.
   - When launched via [`run.sh`](tools/fossify-cipher-cli/run.sh), `bubblewrap` (`bwrap`) isolates `cipher_vault.py` with `--unshare-net --unshare-ipc --unshare-pid --die-with-parent`, binds `$DESKTOP_DIR`, `/media`, `/mnt`, `/run/media`, `$HOME/Persistent`, `/home/amnesia/Persistent`, and custom `-i` / `-o` / directory `-v` arguments writable (`--bind`), while binding `$DIR`, system directories, and `.vault` files read-only (`--ro-bind`)—with `firejail --net=none`, `unshare --user --net`, and Python `sys.addaudithook` fallbacks (unless `--adb` is passed).
3. **Run `./run.sh` (Zero Output Prompt — Unified Auto-Routing via `choose_encrypt_output_dir`):**
   - Unlock `.vault` via `unlock_master_key_with_path` (supporting interactive retry prompts on empty or wrong secrets, or non-interactive `--secret` / `--pattern` / `-v` / `-k` flags). `choose_encrypt_output_dir` asks **no interactive destination prompt** and resolves automatically in order:
     1. Explicit `-o` / `--output` path (if passed on the CLI).
     2. Targetable vault directory (`is_targetable_vault_dir`, e.g., `<USB>/Secrets/.vault` -> `<USB>/Secrets`).
     3. External / non-local `.vault` parent (e.g., `<USB>/.vault` -> `<USB>/Secrets`).
     4. Localized Desktop fallback (`~/Desktop/Encrypted_Output` / `~/Desktop/Sifreli_Cikti`) when a standalone `.vault` resides on Desktop, Home, input, or script directories.
   - Choose either end-to-end USB workflow (optionally wiping RAM sources via `--delete-source` or transferring via `--adb`):
     - **Workflow A — Direct External Vault (No internal copy on phone):** Maintain your vault directly in `<USB>/Secrets/`. `./run.sh` appends newly encrypted `.meta` albums and `.bin` files straight to the drive; connect the USB drive directly to Android to open and play them.
     - **Workflow B — Phone Vault + Unified `<USB>/Secrets/` In-App Sync:** Keep your primary vault on the phone and populate `<USB>/Secrets/` with either:
       - **Scenario 1 (Full copy of `Secrets` on USB):** Tails CLI appends new files alongside existing albums; connect to your phone and run **Settings > Encrypted vault > Sync vault from external drive** (*"Ayarlar > Şifreli Kasa > Harici diskten kasayı eşitle"*). Android skips unchanged mirror files in `O(1)` and imports only new additions.
       - **Scenario 2 (Only `.vault` inside `<USB>/Secrets/`, zero vault media mirrored on USB):** Tails CLI writes only newly encrypted `.meta` album folders / `.bin` files into `<USB>/Secrets/`; Android syncs them into matching phone albums (or lazily creates new encrypted albums / routes bare `.bin` files to **`Default Secret Album`**) using the exact same UI flow, after which you can delete the synced `.bin`/subfolders on USB while keeping `.vault` for next time. Both scenarios run through the 4-stage sync optimization and full bit-by-bit RAM duplicate/collision verification (see [Section 5](#5-device-migration-backup--vault-auto-detection)).

### CLI Behavior, Media Validation & Album Routing

- **Pre-Encryption Supported Media Verification (`SUPPORTED_MEDIA_EXTENSIONS`, `is_supported_media_file`):**
  - Before encrypting, `cipher_vault.py` validates every file extension against the exact gallery-supported formats matching Android `CryptoManager.isSupportedMediaName` and `org.fossify.commons`:
    - **Photos (`PHOTO_EXTS`):** `.jpg`, `.jpeg`, `.png`, `.webp`, `.heic`, `.heif`, `.apng`, `.avif`, `.bmp`, `.wbmp`, `.ico`, `.jxl`, `.jfif`, `.pjpeg`, `.pjp`
    - **GIF & SVG (`GIF_EXTS`, `SVG_EXTS`):** `.gif`, `.svg`
    - **RAW (`RAW_EXTS`):** `.dng`, `.cr2`, `.cr3`, `.nef`, `.nrw`, `.arw`, `.srf`, `.sr2`, `.orf`, `.rw2`, `.pef`, `.raf`, `.srw`, `.x3f`, `.erf`, `.mef`, `.mos`, `.mrw`, `.dcr`, `.kdc`, `.3fr`, `.fff`, `.iiq`, `.rwl`
    - **Videos (`VIDEO_EXTS`):** `.mp4`, `.mkv`, `.webm`, `.avi`, `.3gp`, `.3gpp`, `.3g2`, `.mov`, `.m4v`, `.ts`, `.mts`, `.m2ts`, `.qt`, `.flv`, `.f4v`, `.wmv`, `.asf`, `.mpg`, `.mpeg`, `.mpe`, `.vob`, `.ogv`, `.rm`, `.rmvb`, `.divx`
  - Unsupported files (e.g., `.txt`, `.pdf`, `.md`, `.zip`) as well as existing `.bin` and `.`-prefixed hidden files are skipped with warnings, counted in the summary, and left **untouched** even if `--delete-source` is specified.
- **Default Secret Album Routing (`VAULT_DEFAULT_ALBUM_NAME`):**
  - Root-level files placed directly in the input folder (outside any subfolder) automatically route to **`Default Secret Album`** (`__VAULT_DEFAULT_ALBUM__`), reusing any existing default album subfolder (including legacy localized names such as `"Varsayılan Gizli Albüm"` / `"Default Hidden Album"`) or creating a new randomized 6-character hex subfolder with an `FGMETA2` encrypted `.meta`.
- **`.meta`-Aware Subfolder Matching & Creation (`scan_existing_vault_albums`, `get_or_create_vault_album`):**
  - Before creating folders, `cipher_vault.py` unwraps `.meta` (and legacy `.fmeta`) names of immediate subdirectories in the target vault (ignoring `.`-prefixed directories, `JSON/`, and `$$VAULT_RECYCLE_BIN$$`).
  - Input subfolders match existing encrypted albums cleanly (**exact match first**, then trimmed **case-insensitive match**) to append new `.bin` files into the existing 6-character hex folder, or create a new randomized 6-character hex subfolder with `FGMETA2` `.meta` when absent.
  - Nested subdirectories (e.g., `To_Encrypt/Vacation/Day1/img.jpg`) flatten to their top-level album name (`Vacation`) to match Android's single-level vault hierarchy.
  - `.nomedia` is placed at `Secrets/.nomedia` rather than inside normal or default album subfolders (only `.`-prefixed hidden albums receive an inner `.nomedia`), matching `ExcludedMenuPolicy.isEncryptedAlbumExcluded`.
  - Mixed root-level files and album subfolders are processed seamlessly in a single pass.
- **Virtual Albums (`JSON/`) Isolation:**
  - `Secrets/JSON/` Stealth Virtual Albums have **no connection** to `cipher_vault.py`. They are completely ignored during vault album scanning and encryption, and are managed solely inside the Android application.
- **Android-Compatible Encrypt-Only Stream Pipeline (`encrypt_file`):**
  - `cipher_vault.py` is strictly **Encrypt-Only** (all decryption commands, `.zip` extraction/decryption, and plaintext readback helpers have been removed so media is decrypted solely inside the offline Android app).
  - Encryption (`encrypt_file`) unwraps `.vault` via `Argon2id` + `AES-256-GCM`, derives HMAC-SHA256 domain subkeys (`DOMAIN_HEADER_KEY`, `DOMAIN_CONTENT_ENC_KEY`, `DOMAIN_CONTENT_MAC_KEY`) from the 256-bit Master Key, encrypts metadata headers (including 320px JPEG thumbnails for photos via Pillow) with `AES-256-GCM`, and streams payloads with `AES-256-CTR` + `Poly1305-AES` (`MAGIC_V2` `FGVLTENC`, `VERSION_SYMMETRIC_AUTH = 3`).

## 9. Favorites & Virtual Albums Import / Export

Calypso Gallery provides a unified **Export / Import** mechanism in **Settings** (`SettingsActivity`) for backing up and restoring **Favorites** and **public Virtual Albums**.

> [!CAUTION]
> **Security Note:** Do **not** import backups from untrusted sources. Imported `.zip` archives and JSON manifests are parsed directly by the application and can reference arbitrary local file paths, alter or overwrite your Favorites list (when using replace mode), and create new Virtual Albums in your library. Only import backup packages that you created yourself or received from a source you explicitly trust.

### Backup Format: JSON Inside a `.zip` Archive

Backups are stored as **JSON files packaged inside a `.zip` archive** (`application/zip`). This keeps both Favorites metadata and individual Virtual Album manifests portable in a single file while preserving full file and folder identity descriptors (`MediaIdentity` and `FolderIdentity`).

```text
<appName>-favorites_<YYYY-MM-DD_HH-mm-ss>.zip
├── Favorites/
│   └── favorites.json
└── Virtual albums/
    ├── Vacation.json
    ├── Roadtrip.json
    └── ...
```

- **`Favorites/favorites.json`**: Created when at least one valid favorite exists. Serialized from `ReferenceBackupManager.FavoritesBackup`.
- **`Virtual albums/<album>.json`**: Created for each non-hidden virtual album. Serialized from `VirtualAlbumSyncManager.VirtualAlbumBackup`. If two albums produce the same filename, `FavoritesAndVirtualAlbumsBackupManager.resolveUniqueZipFileName` appends a numeric suffix (`Album(1).json`, `Album(2).json`, etc.).
- **Excluded Data:** Hidden/stealth virtual albums (`isHidden == true`), encrypted vault media (`Secrets/`), and items in the recycle bin (`recycleBinPath`) are **never** included in exports.

### Export Flow

Implemented across `SettingsActivity` (`setupExportFavorites`, `startExportFavoritesFlow`, `exportFavoritesTo`) and `FavoritesAndVirtualAlbumsBackupManager` (`hasDataToExport`, `exportToStream`, `writeExportPackage`):

1. **Availability Check (`hasDataToExport`):** Verifies whether `favoritesDB.getValidFavoritePaths()` is non-empty or `virtualAlbumsDB.getAllAlbums()` contains at least one non-hidden virtual album (`!it.isHidden`). If neither exists, a *"No items found"* toast is shown.
2. **Destination Selection (`startExportFavoritesFlow`):**
   - **Android 10+ (API 29+ / `isQPlus()`):** Opens `ExportFavoritesDialog` for the filename, then launches Android's Storage Access Framework (`Intent.ACTION_CREATE_DOCUMENT`) with MIME type `application/zip`.
   - **Android 9 and below:** Requests `PERMISSION_WRITE_STORAGE`, opens `ExportFavoritesDialog` for the destination path, and writes directly to the chosen file.
3. **Data Collection (`exportToStream`):**
   - **Favorites:** Queries `favoritesDB.getAll()` and filters to paths present in `favoritesDB.getValidFavoritePaths()`.
   - **Virtual Albums:** Queries `virtualAlbumsDB.getAllAlbums().filter { !it.isHidden }`, excluding paths marked as deleted for each album (`getDeletedPathsForAlbum`) and any path under `recycleBinPath`.
4. **JSON Serialization & ZIP Packaging (`writeExportPackage`):**
   - Uses `GsonBuilder().setPrettyPrinting().create()` to serialize `FavoritesBackup` (`version`, `favorites`) and `VirtualAlbumBackup` (`version`, `name`, `createdTs`, `isHidden`, `parentPhysicalPath`, `items`) into UTF-8 entries inside a `ZipOutputStream`.
   - The exported `.zip` output is identical whether or not all-files storage access is granted.

### Import Flow

Implemented across `SettingsActivity` (`setupImportFavorites`, `importFavorites`, `applyFavoritesAndAlbumsImport`), `FavoritesAndVirtualAlbumsBackupManager.parseImportPackage`, and `FavoritesAndVirtualAlbumsImporter`:

1. **File Selection (`setupImportFavorites`):**
   - **Android 10+ (`isQPlus()`):** Launches `Intent.ACTION_GET_CONTENT` accepting `application/zip`, `application/x-zip-compressed`, `application/octet-stream`, and `text/plain`.
   - **Android 9 and below:** Requests `PERMISSION_READ_STORAGE` and opens `FilePickerDialog`.
2. **Package Parsing (`parseImportPackage`):**
   - Inspects header bytes (`isZipArchive` checks for ZIP magic bytes `0x50 0x4B` followed by `0x03`, `0x05`, or `0x07`):
   - **ZIP Archive (`parseZipPackage`):** Iterates entries via `ZipInputStream`, normalizes `\` to `/`, strips leading `/`, and **rejects path traversal** (`..` segments). Only `.json` files are processed:
     - Entries under `Favorites/` (case-insensitive) are parsed as `FavoritesBackup` (`parseFavoritesJson`), filtering out null/blank `fullPath` entries.
     - Entries under `Virtual albums/` or `Virtual Album Saves/` (`CIPHER_VIRTUAL_ALBUMS_DIR_NAME`) are parsed as `VirtualAlbumBackup` (`parseVirtualAlbumJson`). Encrypted/stealth virtual albums (`isHidden && encryptedPayload != null`) are ignored. Legacy `mediaPaths` arrays are supported when `items` is absent, and `.json` filenames serve as fallback album names.
   - **Legacy / Plaintext Fallback (`parseLegacyOrPlainPackage`):** Non-ZIP inputs starting with `{` are parsed as a single `FavoritesBackup` or `VirtualAlbumBackup` JSON object; otherwise each non-empty line is treated as a plain favorite file path.
3. **Favorites Conflict Resolution (`ImportFavoritesConflictDialog`):**
   - If imported favorites are present and `hasExistingFavorites` is true, the user chooses between:
     - **Merge (`FavoritesImportMode.MERGE`):** Keeps existing favorites and adds/updates imported ones.
     - **Replace (`FavoritesImportMode.DELETE_EXISTING`):** Clears `favoritesDB`, resets favorite flags in `mediaDB`, and removes the `FAVORITES` entry in `directoryDB` before importing.
4. **Restoring Favorites (`importFavoritesList` & `importSingleFavorite`):**
   - Resolves each entry via `resolveExistingPath` (direct path check, falling back to `MediaIdentityResolver.resolve(...)` using `MediaIdentity` and `FolderIdentity`).
   - Rejects paths inside `recycleBinPath` or `CryptoManager.isVaultMediaPath(...)`.
   - Inserts new `Favorite` records (updating `mediaDB.updateFavorite(resolvedPath, true)`) or enriches missing `fingerprint`/`folderSignature` fields on existing entries.
   - If shared-storage write access is granted (`canWriteInternalBackups`), syncs `Calypso Gallery/Favorites/favorites.json` via `ReferenceBackupManager.saveFavorites(context)`.
5. **Restoring Virtual Albums (`importVirtualAlbumsList` & `insertImportedVirtualAlbum`):**
   - Assigns collision-safe album names via `resolveUniqueVirtualAlbumName` (appending `(1)`, `(2)`, etc.) so existing virtual albums are never overwritten.
   - Inserts a new non-hidden `VirtualAlbum` (`isHidden = false`) and bulk-inserts resolved `VirtualAlbumItem` rows (rejecting `recycleBinPath` and vault paths, deduplicating case-insensitively, and preserving `UNRESOLVED` paths when the parent directory does not exist on disk).
   - If shared-storage write access is granted (`canWriteInternalBackups`), writes `Calypso Gallery/Virtual Album Saves/<album>.json` via `VirtualAlbumSyncManager.saveAlbumToFile(context, newAlbumId)`; otherwise imported data stays safely in the app's internal Room database.

## 10. Timestamp Preservation (`lastModified` / `dateTaken`) & Metadata Risks

This section documents how `lastModified` and `dateTaken` are handled across copy, move, encryption, decryption, and external vault synchronization, together with the **Bit-to-Bit + Metadata Equivalence Architecture** that keeps distinct historical and re-uploaded versions of bit-identical media safe.

### Bit-to-Bit + Metadata Equivalence Architecture

When a user holds both an historical copy (e.g., `2021`) and a re-uploaded/re-downloaded copy (e.g., `2026`) of the exact same bit-identical image or video, pure payload byte equality treats the two files as redundant duplicates. Across operations that skip conflicts (`Copy`, `External Sync`) or delete identical sources (`Encrypt`, `Decrypt`, `Move`), pure bit-to-bit matching would either drop the second timestamped copy or wipe one version in favor of the other.

To prevent this while preserving idempotency on repeated operations, deduplication across the codebase enforces **Dual-Criterion Equivalence (Payload Bits + Timestamp Metadata)**:

1. **Timestamp Equivalence Helpers (`TIMESTAMP_EQUIVALENCE_TOLERANCE_MS = 2_000L`):**
   - `CryptoManager.areTimestampsEquivalent(tsA, tsB)` treats two positive timestamps as equivalent if and only if $|tsA - tsB| \le 2000\text{ ms}$. The `2,000 ms` window absorbs FAT32/exFAT 2-second `mtime` granularity and MediaStore second-level rounding (`* 1000`) while separating historical vs. re-uploaded copies cleanly.
   - `CryptoManager.areMediaTimestampsEquivalent(lastModA, dateTakenA, lastModB, dateTakenB)` and `areEncryptedTimestampsEquivalent(metaA, metaB)` require equivalent `lastModified` **and**—whenever both sides carry a positive `dateTaken`—equivalent `dateTaken`.
2. **Gated Operations (Duplicate Skip, Wipe/Delete & Conflict Inspection):**
   - **`encryptFileToDirectory` / `decryptFileToDirectory` / `copyOrMoveEncryptedFileToDirectory`:** Only trigger `IDENTICAL_SKIP` or `deleteSourceOnIdentical` source removal when **both** bit-for-bit bytes and `areMediaTimestampsEquivalent` match. Differing-timestamp copies with identical bits proceed cleanly into `CONFLICT_KEEP_BOTH` collision naming (`<stem>(1)<ext>`).
   - **`inspectTransferConflict`, `findContentConflictInTarget`, `findIdenticalPlainFileInDir` & `CopyMoveRunner` (`isDuplicatePlainInTarget`):** Smart conflict detection and inline copy/move conflict checks return `IDENTICAL_SKIP` only when both bytes and timestamps match within tolerance; otherwise an exact-name collision with different timestamps surfaces as `NAME_CONFLICT`, and repeated transfers find the matching timestamped `(n)` variant across the collision family for idempotent skipping.
   - **`syncVaultFromExternalDirectory` (Stages 2 & 3/4):** Stage 2 (`isFastMacMatchDuplicate`) and Stage 3/4 (`compareEncryptedStreamAndVerifySourceMac`) require `areEncryptedTimestampsEquivalent(sourceMeta, existingMeta)` before marking `skippedDuplicateCount`. A re-uploaded external `.bin` with a newer/older timestamp is imported and preserved under `<stem>(1)<ext>`; syncing that same file again matches the newly imported `(1)` variant and skips cleanly.
3. **Symmetric Collision Family & `preExistingPaths` Sibling Protection:**
   - `CryptoManager.isSameOrCollisionVariant` compares `stripCollisionIndex(candidateName)` and `stripCollisionIndex(incomingOriginalName)` symmetrically (`photo.jpg` matches `photo(1).jpg` in both directions), and `TargetPlainIndex` / `TargetEncryptedIndex` key `byFamilyLower` by stripped base name.
   - Because batch operations (`encryptFolder`, `decryptFolder`, `CopyMoveRunner`) reuse a shared index per destination folder, `TargetPlainIndex` and `TargetEncryptedIndex` accept an optional `preExistingPaths` snapshot. Only **exact** filename collisions or collision variants already present before the batch started can participate in duplicate skipping—so legitimate same-folder siblings sharing identical bytes and timestamps (`photo.jpg` and `photo(1).jpg`) never cannibalize each other mid-batch.
4. **Reference & Identity Timestamp Scoping (`VirtualAlbums.kt` & `MediaIdentityResolver.kt`):**
   - `markReferencesOnEncrypt` and `markReferencesOnDecrypt` filter dormant fingerprint-based reconnections by `areTimestampsEquivalent` when both timestamps are positive, preventing a 2026 copy from latching onto a 2021 dormant Virtual Album or Favorite entry (and vice versa).
   - `MediaIdentityResolver.scoreCandidate` and `matchesCheapSignature` use `areTimestampsEquivalent` instead of strict millisecond equality (`==`), preventing FAT32 2-second rounding on external SD/OTG cards from breaking identity continuity.

> [!NOTE]
> **Special Timestamp Exception vs. General File Metadata:** Unlike EXIF payloads or image/video bitstreams (which are already covered bit-for-bit by payload comparison), filesystem `lastModified` and out-of-band capture timestamps (`dateTaken`) are external temporal context. This architecture treats **only** `(lastModified, dateTaken)` equivalence—rather than arbitrary metadata properties or collision indices (`matchCollisionVariants`)—as a separator between distinct temporal instances, avoiding unrequested duplicate bloat on identical re-saves while keeping timestamped history intact.

### Residual Operational Notes & Edge Cases

1. **Tails OS / RAM Staging Timestamp Hygiene Before CLI Encryption:**
   - `cipher_vault.py` records `stat.st_mtime` alongside extracted EXIF `date_taken`. If plaintext files are copied into RAM staging (`~/Desktop/To_Encrypt`) without timestamp preservation (e.g., plain `cp` instead of `cp -p` / `rsync -a`), `lastModified` reflects the staging time even though EXIF `date_taken` is preserved.
2. **SAF / Read-Only Target OS Limits:**
   - POSIX `File(dest.path).setLastModified(...)` fails silently on SAF-only external roots lacking direct POSIX write access; on FAT32/exFAT drives, `mtime` is rounded by the OS to 2-second intervals (handled cleanly by the `2,000 ms` equivalence window).
3. **Non-Timestamp Deduplication Consequences:**
   - **Reference Consolidation When Matching Both Bits & Timestamps:** When `deleteIdenticalSource = true` and both payload bytes and timestamps match within tolerance, `markReferencesOnEncrypt` / `markReferencesOnDecrypt` consolidates Favorites and Virtual Album references onto the single surviving file.
   - **External `MediaStore._ID` Breakage on Source Cleanup:** Deleting a true duplicate source copy removes its original `MediaStore` row/path, which can break third-party shortcuts pinned specifically to that path.
   - **Destructive Deduplication Must Never Use `fastSampling`:** `encryptFolder` and `decryptFolder` force `fastSampling = false` (full byte-by-byte stream verification + Poly1305 MAC check) whenever deleting source files, avoiding false positives on large videos sharing identical headers/trailers.
